A LoRA adapter, end to end

Compose → chat template → tokenizer → prefill → switch → control-token replacement → decoder → LoRA kernels → decode. Every number below was read off a real composed checkpoint or executed, not recalled.

The checkpoint used throughout

barha/granite-switch-4.0-350m-demo — base granite-4.0-350m, 3 adapters, composed from main (its template still uses the older skip_next_start_of_role name).

Caveat stated once, up front: all three of its adapters are declared technology: "alora". To show the LoRA branch with real output rather than a hand-written guess, the renders below flip one adapter's declared type from 'alora' to 'lora' in the shipped template's adapter_map and re-render. That exercises the real template code; nothing else is altered.

1. The whole pipeline on one page

One sentence: a LoRA adapter is turned on by a token in the prompt, and that token is erased before the model sees it. Everything else is bookkeeping around those two facts.

COMPOSE TIME (once, offline)
  base model + PEFT adapter dir
        |
   [1] add control token to tokenizer      <|text-to-json|> -> id 100353
   [2] probe the substitute token          no-adapter render starts with 100264
   [3] rewrite the chat template           lora -> emit token at position 0
   [4] stack + pre-scale LoRA weights      lora_B *= alpha/rank
   [5] resize embeddings, init ctrl rows
   [6] write config + 1 extra KV slot      num_hidden_layers 28 -> 29
        |
        v
   checkpoint on disk (config.json, chat_template.jinja, model.safetensors)

REQUEST TIME (per request)
   apply_chat_template(msgs, adapter_name="text-to-json")
        |
   [7] render     ids[0] = 100353   (replaces the 100264 that would be there)
   [8] tokenize + vLLM prefix-cache hash over those ids
        |
   [9] PREFILL: switch attention  ->  adapter_indices = [2,2,2,...]
  [10] token exchange            ->  ids[0] rewritten 100353 -> 100264
  [11] embed modified ids        ->  sequence now identical to no-adapter render
  [12] adapter_indices - 1       ->  Punica token_lora_mapping
  [13] 28 decoder layers, LoRA added per token
        |
  [14] DECODE: the +gain key sits in the KV cache, so each new token
       re-reads it and stays on adapter 2

2. Part A — compose time

Add one control token per adapter to the tokenizer

The token string is mechanical: <|{adapter_name}|>. It is added as a special token, so the tokenizer never splits it.

special_tokens.append(f"<|{adapter_name}|>")
num_added = tokenizer.add_special_tokens(
    {"additional_special_tokens": special_tokens}
)

src/granite_switch/composer/tokenizer_setup.py:194-199

In the real checkpoint the base vocab of 100352 grows by 3:

tokenidadapter index
<|cti-technique-mapping|>1003521
<|text-to-json|>1003532
<|genai-attack-vector|>1003543

config.json: adapter_token_ids [100352, 100353, 100354], vocab_size 100355

Note the index convention that holds for the rest of the pipeline: 0 means base / no adapter, and adapter slot i is index i+1. There is no token for "base" — base is the absence of any control token.

Probe which token the control token will impersonate

The control token is going to sit at position 0, displacing whatever normally lives there. Compose asks the tokenizer what that is, by rendering a throwaway chat and taking the first id:

probe_text = tokenizer.apply_chat_template(
    [{"role": "user", "content": "probe"}],
    tokenize=False, add_generation_prompt=False,
)
ids = tokenizer(probe_text, add_special_tokens=False).input_ids
sub_id = ids[0]

src/granite_switch/composer/compose_granite_switch.py:121-137

Verified by running it on this checkpoint's tokenizer: a no-adapter render starts

'<|start_of_role|>system<|end_of_role|>You are a helpful assistant. ...'
ids[:6] = [100264, 9125, 100265, 2675, 527, 264]
             ^^^^^^ <|start_of_role|>

so sub_id = 100264. That value is written into the config as adapter_substitute_token_ids — here [100264, 100264, 100264]. For a Granite 4.2 ChatML template the same probe yields <|im_start|> (100256) instead; nothing is hardcoded.

The assumption this rests on. The template must emit a constant ids[0] regardless of message content, system prompt, or generation-prompt flag. True for Granite 4.x, pinned by tests/composer/test_lora_substitute_probe.py. A future template that branched at position 0 (say, BOS only when no system message) would silently break this — the probe would still return a valid id, just the wrong one for some render modes.

Rewrite the chat template

Two things are injected: a lookup table of adapter name → (token, type), and a prefix rule. The prefix rule is the whole LoRA placement policy:

{#- For lora adapters: insert activation token at the very beginning -#}
{%- if adapter_token and adapter_type == 'lora' %}
{{- adapter_token }}
{%- set ns.skip_next_role_marker = true %}
{%- endif %}

src/granite_switch/composer/tokenizer_setup.py:332-336 (shipped checkpoint has the older name skip_next_start_of_role, chat_template.jinja:53-56)

The second line matters as much as the first. Without it you would get the control token plus the role marker, i.e. two consecutive near-identical embeddings after the swap — a shape the base model never saw in training. So the template emits the control token and suppresses the very next role marker, making it a replacement rather than an insertion:

{%- if ns.skip_next_start_of_role %}{%- set ns.skip_next_start_of_role = false %}
{%- else %}{{- '<|start_of_role|>' }}{%- endif %}

chat_template.jinja:89 (shipped)

Stack the LoRA weights, pre-scaled

PEFT ships one adapter as its own pair of matrices per target module. Compose stacks all adapters into a single tensor with the adapter as the leading dimension, so the runtime can gather per token:

if is_lora_a:
    stacked[target_name][adapter_idx, 0, :adapter_rank, :] = tensor
else:
    scaling_factor = adapter_alpha / adapter_rank
    stacked[target_name][adapter_idx, 0, :, :adapter_rank] = tensor * scaling_factor

src/granite_switch/composer/weight_transfer.py:547-550

Two design choices are visible there. Ranks are padded to max_lora_rank, so mixed-rank adapters coexist (the tail stays zero and contributes nothing). And alpha/rank is folded into lora_B at compose time, so the inference path has no scalar multiply — consistent with the runtime comment "lora_B weights are PRE-SCALED by (alpha/rank) during model loading" at src/granite_switch/hf/core/lora.py:53.

Real shapes from the checkpoint ([num_adapters, 1, ...], 392 of 565 tensors are LoRA):

tensorshapenote
layers.0.self_attn.o_proj.lora_A[3, 1, 32, 1024]rank 32, in 1024
layers.0.self_attn.o_proj.lora_B[3, 1, 1024, 32]pre-scaled
qkv_proj.lora_A_slices.0/1/2[3, 1, 32, 1024] eachduplicated — Q/K/V share the input space
qkv_proj.lora_B_slices.0[3, 1, 1024, 32]Q — chunked from the fused output dim
qkv_proj.lora_B_slices.1[3, 1, 256, 32]K — 4 kv heads × 64
qkv_proj.lora_B_slices.2[3, 1, 256, 32]V

That split is the fused-projection adaptation: this backbone has one fused qkv_proj where PEFT trained three separate ones, so lora_A is duplicated across slices and lora_B is chunked along dim 0 (weight_transfer.py:575-596, split_type "duplicate" / "chunk_dim0").

Resize embeddings, then fix the new rows

resize_token_embeddings gives each newly-added control token a random row. Compose overwrites it with the substitute's row:

emb[ctrl_id].copy_(emb[sub_id])
if lm_head is not None and lm_head.weight is not emb:
    lm_head.weight[ctrl_id].copy_(lm_head.weight[sub_id])

src/granite_switch/composer/compose_granite_switch.py:216-218

Why this exists, precisely. At inference the input row for a control token is never read — step 10 rewrites the id first. The row matters on the output side: Granite 4.x ties embeddings (tie_word_embeddings: true in this checkpoint, and there is no separate lm_head.weight tensor), so a random input row is a random logit for that token. Two compose runs then disagree about the top-1 at a low-confidence position, and HF vs vLLM disagree with them — a flaky argmax test with no real bug behind it. Copying the substitute row makes it config-derived and reproducible.

Verified on the shipped checkpoint: this fix is newer than it. emb[100352] and emb[100264] are not equal there (0.00775, 0.00124, ... vs -0.00043, -0.00128, ...). It predates _init_control_token_embeddings, which is consistent with its template still using the older skip_next_start_of_role spelling. Harmless for routing — routing reads ids, not embeddings — but its control-token logits are whatever the RNG produced.

Write the config, including one extra KV-cache slot

The switch is a real attention layer and needs its own cache slot. Compose accounts for it by inflating num_hidden_layers, and the runtime subtracts it back out:

if config.num_adapters > 0:
    layer_offset = self.switch.num_cache_layers      # 1 for SingleSwitch
    num_decoder_layers = config.num_hidden_layers - layer_offset

src/granite_switch/vllm/granite_switch_model.py:178-180

Verified on disk: num_hidden_layers: 29, while the actual decoder tensors are model.layers.0 … model.layers.27 — 28 layers. 28 + 1 = 29. The inflation count is pinned to the switch class by tests/composer/test_switch_cache_layers.py:62-71.

The switch itself carries no learned parameters. The only switch tensor in the whole checkpoint is the lookup table:

lut[100352] = 100264
lut[100353] = 100264
lut[100354] = 100264
lut[100264] = -1        # not a control token

Render the prompt

>>> tok.apply_chat_template(msgs, add_generation_prompt=True,

Both are 31 tokens. Diffing the id lists:

differ at positions: [0]

That is the entire footprint of activating a LoRA adapter: one token id, at position 0, replacing the role marker. The prompt does not get longer, and no other position moves.

Tokenize, and let vLLM hash it

Nothing in this repo participates — grep -rn "prefix_caching\|block_hash" src/ returns nothing. vLLM chops the request's ids into blocks and hashes each one chained to its parent:

block_tokens = request.all_token_ids[start_token_idx:end_token_idx]
block_hash = hash_block_tokens(
    caching_hash_fn, prev_block_hash_value, block_tokens, extra_keys
)
prev_block_hash_value = block_hash

vllm/v1/core/kv_cache_utils.py, get_request_block_hasher (fetched from vllm-project/vllm@main; this repo pins vllm>=0.19.1,<0.20.0, so line numbers drift)

The adapter id never enters the hash and does not need to: the control token is at position 0, so it is inside block 0, and every later block hash chains off block 0's. Request A with 100352 and request B with 100353 diverge at the first hash and share no block anywhere. The extra_keys LoRA channel tracks vLLM's native LoRARequest, which granite-switch never sets — and that is fine.

Unexercised in CI: every vLLM test here passes enable_prefix_caching=False (tests/integration/test_multi_switch_vllm_generate.py:85, tests/vllm/_generation_equivalence_worker.py:156), set for determinism with no comment claiming a hazard. The argument above is from data dependencies, not from a passing prefix-cache test.

Prefill: the switch turns the token into a per-token index

The switch runs before the decoder and answers one question per token: which adapter applies here? It answers with attention, because attention is the operation vLLM already batches, caches and shards correctly.

matches    = input_ids.unsqueeze(1) == adapter_token_ids.unsqueeze(0)
is_control = matches.any(dim=1)
adapter_ids = torch.where(is_control, matches.long().argmax(dim=1) + 1, 0)

gain_sign = (2.0 * is_control.to(self.dtype) - 1.0) * self.effective_gain
k[:, :, 0] = gain_sign.unsqueeze(1)          # +gain at control, -gain elsewhere
v[:, :, 0] = adapter_ids.to(self.dtype)      # the payload
q[:, :, 0] = 1.0                             # constant probe

attn_output = self.attn(q, k, v)
adapter_indices = torch.clamp(torch.round(attn_output[:, 0]), 0, self.num_adapters)

src/granite_switch/vllm/switch/single.py:171-217 (condensed)

pos:       0            1        2        3      ...
tok:   <|text-to-json|> "system" ...      ...
k[0]:     +15          -15      -15      -15
v[0]:       2            0        0        0
q[0]:       1            1        1        1
           |            |        |        |    causal softmax, gain 15
           v            v        v        v
idx:        2            2        2        2      -> adapter 2 on every token

Why it works: with gain 15 the single +15 key beats every -15 key by e^30 ≈ 10^13, so the attention output is the adapter id to ~13 digits and round makes it exact. The gain is pre-divided by attention_multiplier (single.py:70) because the Attention layer applies that scaling itself.

This is a genuine paged-KV vllm.Attention with prefix="switch.layers.0" (single.py:85-93), using backbone head geometry (projection_head_dim: 64, num_key_value_heads: 4 here). vLLM therefore confines each request's switch attention to its own tokens for free — which is why SingleSwitch can ignore the positions argument entirely (single.py:143-149).

Control-token replacement (token exchange)

Same function, last four lines. The control token has done its job; now it is erased:

sub_id_per_pos = self.control_to_substitute_lut[input_ids]
is_control = sub_id_per_pos >= 0
modified_input_ids = torch.where(is_control, sub_id_per_pos, input_ids)

src/granite_switch/vllm/switch/single.py:226-228 (HF twin at hf/switch/single.py:250-252)

One gather plus one select, unconditionally, every step — no tensor.any() gate, because the surrounding decoder is wrapped in @support_torch_compile and data-dependent branching is not allowed there.

The payoff, verified. Apply the checkpoint's own LUT to the LoRA-branch ids and compare against the no-adapter render:

swapped = [lut[i] if lut[i] >= 0 else i for i in lora_ids]
swapped == base_ids   ->   True

The post-swap sequence is identical, id for id, to what the model would have received with no adapter at all. The decoder is not "tolerating" a strange token — it is looking at an ordinary prompt, and the adapter selection has already been extracted into a separate tensor.

Embed the rewritten ids

hidden_states = self.get_input_embeddings(modified_input_ids)
hidden_states *= self.config.embedding_multiplier

src/granite_switch/vllm/granite_switch_model.py:355-357 (embedding_multiplier: 12 in this checkpoint)

A single ordinary lookup. There is no decoder-side LUT, no per-forward scatter, no clone guard, and no special case — the rewrite happened upstream, so the decoder cannot know a control token ever existed.

Convert to Punica convention, once per forward

punica_indices = adapter_indices - 1          # 0=base -> -1=base
self.lora_meta.prepare_and_store(punica_indices, self.lora_ctx)

prepare_tensors passes the mapping straight through (lora_kernel_meta.py:289) and builds the sort / one-hot bucketing beside it; the +1 at :293 is only for that bucketing. Results land on a single shared LoRAContext that all 28 decoder layers read — computed once, not per layer.

Decoder layers apply LoRA per token

Each adapted projection is a SwitchedLoRALinear: base result, plus a gated LoRA contribution driven by the mapping.

ctx = self._lora_ctx
if ctx is not None and ctx.token_lora_mapping is not None:
    ...
    lora_shrink(...)     # x @ A^T   -> [tokens, rank]
    lora_expand(...)     # @ B^T     -> [tokens, out_features]

src/granite_switch/vllm/core/lora.py:321-386, kernels imported from vllm.lora.ops.triton_ops at :49

No alpha/rank multiply appears, because step 4 already folded it into lora_B. The HF backend does the same arithmetic in plain torch, gathering the slice for each active adapter (hf/core/lora.py:140-160) and short-circuiting entirely when no token uses an adapter (:109).

Adapted modules in this checkpoint: lora_target_modules: ['o_proj', 'qkv_proj', 'shared_input_linear', 'shared_output_linear'] — attention output, fused QKV, and both halves of the shared MLP.

For a LoRA-type adapter every token carries the same index, so token_lora_mapping is constant across the sequence. The kernels still run per token; they just all fall into one bucket. Identical code path to aLoRA — only the values differ.

Decode: the KV cache is what remembers

After prefill, generation feeds one token at a time and the control token is gone from input_ids. Nothing re-derives the adapter from the prompt. Instead the switch's +gain key is sitting in its paged cache slot, and the new token's constant query reads it again:

decode step, token 31
  q[0]=1  --attends-->  cached k: [+15, -15, -15, ... ]     (from prefill)
                        cached v: [  2,   0,   0, ... ]
                        own    k:  -15
                     -> 2.0 -> round -> idx = 2    (adapter still on)

This is why the query is a constant 1.0 rather than anything derived from the current token: the current token needs to carry no information at all. The adapter state lives entirely in the cache, which vLLM already pages, evicts and shards correctly.

The output side closes the loop: control-token rows in the (tied) lm_head are copied from their substitutes at compose_granite_switch.py:174, so if the model ever emits a control token it scores like the token it impersonates rather than like a random row.

5. Invariants, and where they can break

invariantenforced bywhat breaks if it fails
Control token is at position 0 for LoRAtemplate prefix, tokenizer_setup.py:332only the tail of the prompt gets the adapter (i.e. aLoRA semantics)
Exactly one role marker survivesskip_next_role_markertwo near-identical embeddings back to back — out of distribution
Substitute == the displaced tokencompose-time probe + test_lora_substitute_probe.pyswap injects the wrong embedding at position 0
Switch K/V are a pure function of idssingle.py:174-198prefix-cache reuse would become unsound
num_hidden_layers includes the switch slottest_switch_cache_layers.pyoff-by-one layer count; cache slot mis-assigned
lora_B carries alpha/rankweight_transfer.py:549adapter strength off by that factor

Known limits, stated in the code

  • One adapter per request. Softmax averages: two control tokens with values 1 and 2 give (1+2)/2 = 1.5 → 2. Not a precedence rule — an arithmetic accident. single.py:139-142: "SingleSwitch has no mechanism to transition back to base mid-sequence." This is what MultiSwitch exists to fix.
  • Position 0 in a hiding group shifts hidden_count by 1, giving a one-position RoPE offset (CLAUDE.md gotcha 7). Accepted: detection is exact and RoPE tolerates it.
  • Prefix caching is untested here — see step 8.
