upgrade-vllm

An autonomous pipeline that moves granite-switch onto newly released vLLM lines and hands back a reviewable PR.

vLLM releases faster than this repo tracks it. The vllm extra in pyproject.toml claims a contiguous range of supported lines, so every release widens a gap between what is claimed and what has actually been tested. This skill closes that gap without supervision.

The only human step is reviewing and merging the PR. Invoking the skill is the authorization for everything else — branching, editing code, relocking, dispatching GPU runs, opening the PR.

What it guarantees

  • One PR for all new lines. The range claim moves in one reviewable change, not one PR per version.
  • Every added line is verified independently — CPU, GPU and both eval tiers. Testing the newest and inferring the rest is explicitly not allowed.
  • Capability gating, never version numbers. Detection is hasattr / try: import. There is currently zero version branching in src/.
  • Proof tables in the PR body — one column per added line, a check only where a gate actually ran on that line.

A green run is not proof a gate ran

pytest exits 0 when every test skips, the pod then prints ALL GPU TESTS PASSED, and the workflow posts success. Measured, not hypothesised: one run collected 4 eval tests, skipped all 4 because no checkpoint was staged, and reported PASSED in 0.03 s. The dispatcher now fails a green run whose log contains no N passed, so the only check mark you can write is one a real test earned.

The ten phases

  1. Preflight. gh authenticated, Maintain/Admin on the repo, uv 0.8.4, SSH push, clean tree. Abort on any failure — an unattended run cannot recover from a missing tool.
  2. Detect the gap. Compare the supported ceiling against released lines on PyPI. Empty gap means stop. No empty PR.
  3. Branch from origin/main directly, without ever checking main out. Checking main out would delete the skill from the working tree on any clone where it is not yet on main — and a deleted skill has no later phases left to read.
  4. Research what actually broke. Diff upstream over only the API surface this repo touches, and read the commits responsible. The worst case is a deleted hook whose override is silently never called again. That shows up as a feature quietly not working, never as a failure — so the fix gets a test asserting the effect, not the call.
  5. Port src/ and tests/. Apply fixes with capability gating, and decide explicitly whether the new line forces the floor or a dependency ceiling up.
  6. Plumbing. Add each line's dependency groups, widen the extra, regenerate the uv conflicts table, relock with the pinned uv. This is also where per-line GPU evidence is bought — see below.
  7. CPU gate, locally, before pushing. Pre-commit over all files, plus the unit suite. Burning a CI run on something reproducible locally wastes everyone's time.
  8. Commit, push, open a draft PR. One commit per concern, DCO-signed.
  9. Drive the gates to green. Dispatch per line × per suite, in parallel; collect each leg's conclusion and URL as it lands. Budget of 5 fix attempts per leg — exceeding it means stop and report rather than thrash.
  10. PR body and hand-off. Generate the proof tables, then mark the PR ready. Never merge. The hand-off is a ready PR.

The one mechanical trick: one commit per line

The GPU workflow does not contain its own test legs. A script baked into the runner image reads the tested commit's own pyproject.toml and emits at most two legs: one from the dev group (the floor) and one from the dev-latest alias (the ceiling). No edit a PR can make will add a third.

So per-line coverage is bought differently: make each added line be dev-latest at some commit, and dispatch at that commit's sha. Workflow concurrency is keyed on the sha, so these runs go in parallel instead of cancelling each other.

The floor is re-tested on every dispatch, every gap line gets its own leg, and the final commit leaves the alias on the true ceiling — which is also the only state allowed to merge. A merge check fails while the alias is parked mid-range, because that would leave the top supported line permanently untested by CI.

Both --ref and --sha, and they mean different things

--ref picks which workflow file runs; --sha picks which commit gets checked out. Letting the sha default is the trap: every dispatch would test the branch tip, so each intermediate line would silently report the ceiling's result — a table full of check marks that proves the top line N times and the others never. The leg label in each result is the receipt that this went right.

Two eval tiers, both required

Neither substitutes for the other: a dead adapter and a degraded adapter are different failures, and tier 1 cannot see the second one. A model that answers confidently and wrongly has a perfectly normal top-k distribution.

Tier 1 compares top-k output distributions against a committed baseline. Two properties of that measurement are load-bearing, and each one was a false positive before it was fixed:

  • It is teacher-forced. Both the baseline and the check push the baseline's recorded continuation through the model, so every compared position sits on a byte-identical prefix. A self-conditioning greedy rollout cannot work here: one flipped near-tie desynchronizes the prefix and every later position then compares unrelated sentences.
  • It compares only below the capture width. At the very edge of the captured top-k, a token ranked just inside one run and just outside the other contributes nearly its whole mass to the metric — an artifact of truncation, not a distribution difference.

Never re-record a baseline, never widen a threshold

A failure here is the signal the whole upgrade was looking for; adjusting the reference to make it pass destroys the gate. The cheap diagnostic that separates a real regression from a broken measurement: if a failure reproduces identically across vLLM lines — including the line the baseline was recorded on — it is a defect in the metric, not stale data. A property of one version cannot be identical on two.

When it stops and asks

Routine steps are pre-authorized and run without prompting. There are exactly four reasons to stop:

  • Preflight fails — the run cannot complete unattended anyway.
  • A gate is still red after 5 fix attempts — report with the log instead of thrashing.
  • A scored eval drifts — accepting a quality change is the user's decision.
  • The floor must rise — widening the supported range is routine; narrowing it is not.
