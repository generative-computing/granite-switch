# Agent race: running and recording it

The agent race pits two ways of serving agents that switch adapters against
each other on one GPU: granite-switch's Shadow Residual (SR), and stock vLLM
serving the same adapters as LoRAs. Its page, `docs/agent_race.html`, lives on
main, with what it shows and the races it holds (main's `docs/AGENT_RACE.md`).
This branch holds the code that runs and records the races, because it runs on
this benchmark's harness: the switch benchmark's scripts, the composer step,
the switching settings and the jobs.

## What races

**The lanes:**

| Lane | Serving | At an adapter switch |
|---|---|---|
| `gs-sr-vllm` | granite-switch SR: the 64 SR adapters composed by the commit, the switch benchmark's shadow-residual arm | nothing: its K/V come from the base model, so one generation runs until a tool call |
| `lora-vllm` | stock vLLM serving the 64 LoRA adapters (its native-lora arm) | ends the request, waits the round trip to the agent (2–10 ms, slept for real), and starts a new one, prefilling the agent's whole context again |

**The agents** run in slots: the next starts as soon as any running one finishes.
Each has a prompt of its own (256 to 16,384 tokens). Both lanes read one
workload file, so an agent's prompt, adapter schedule and length are the same in
both. Two kinds:

- **Fixed steps:** the [switching workload](ADAPTER_BENCHMARK.md#agents-switching-adapters)'s
  agents, from the switch benchmark's generator (`benchmarks/gen_switching_grid.py`):
  32-token steps, a new adapter at each, over 64 synthetic adapters of rank 32,
  with a tool call after every 256 tokens.
- **ReAct:** the switch benchmark's agent study's agents, from its generator
  (`benchmarks/gen_agent_configs.py`, copied unchanged), built by
  `benchmarks/adapter_eval/race/react.py`. Each walks a ReAct cycle of typed
  steps (think, prepare_call, act, observe, reflect) at the generator's lengths
  and switch rates. Three settings are the race's: 128 to 1,024 tokens per agent
  (the paper's generate 10,000), the switching workload's prompts, and a round
  trip within one datacenter.

**How it is measured:** both lanes run on one GPU, one after the other, each in
an engine of its own with fresh compile caches and after one untimed warm-up
run of the whole fleet, with the prefix cache reset before every run. The page
replays them side by side, each from its own start.

## Running it

1. Run a race on a pod, through the benchmark's script mode, which installs the
   commit and ships the harness. A job ships the race's code only when its
   script is in `race/`, with the switch benchmark's scripts; every other job
   leaves it out, keeping the harness within its size limit:

   ```bash
   benchmarks/adapter_eval/vela/submit.sh script <commit> benchmarks/adapter_eval/race/run_race.py --extra-args "..."
   ```

   It takes the workload's settings from `switching` in `adapters.yaml` and the
   synthetic adapters from the benchmark's cache (built if missing), composes and
   checks the SR checkpoint, runs both lanes, and prints the race into the
   job's log. The page's races and their options:

   | Agents | Per lane | At a time | Tokens per agent | `--extra-args` |
   |---|---|---|---|---|
   | ReAct, classic5 | 64 | 16 | 128–1,024, 16 each | `--agents-kind react --cycles classic5 --concurrency 16 --decode-mix 128,256,512,1024` |
   | fixed steps | 16 | 8 | 512 | `--agents 16` |
   | fixed steps | 64 | 8 | 512 | (the defaults) |
   | fixed steps | 64 | 16 | 1,024 | `--concurrency 16 --decode 1024` |
   | fixed steps | 64 | 16 | 128–1,024, 16 each | `--concurrency 16 --decode-mix 128,256,512,1024` |

   Add `--model granite-4.2-3b` for another model. A mixed workload runs the
   generator once per length, for an equal share of the agents with a seed of
   its own, then shuffles the agents together with a fixed seed, so a rerun
   gives the same workload.

2. Put the race into the page, in a main checkout, from the pod's saved log:

   ```bash
   python -m benchmarks.adapter_eval.race.build_page benchmarks/adapter_eval/vela/local/logs/<job>.log --page <main checkout>/docs/agent_race.html
   ```

   The page keeps one race per configuration: the run replaces the race of its
   own and keeps the others. It refuses a race that carries an absolute path
   anywhere: the page is public, the run's storage is not. The updated page then
   goes to main in a PR of its own.

   The 16-agent race was recorded (2026-10-11) before the recorder kept
   switches; `build_page --add-switches <grid.jsonl> --page <...>` added them
   from its own workload, regenerated by the same generator with the same seed
   and checked against the recorded agents, at the recorded token marks.

## What is recorded

`benchmarks/adapter_eval/race/lane.py` runs a lane: the agent loop
(`run_agent` in `benchmarks/bench_agent_sim.py`), unchanged, through a recording
engine that notes each request's start, first token, tokens and end, and the
engine's count of cached prompt tokens. The gaps between an agent's requests are
its round trips and tool calls, named from its schedule.

A race holds its events (seconds from each lane's start), each lane's agents
(their prompt lengths, switches, tool calls and times), and the run's public
details: model, commit, GPU, library versions, settings. No path on the run's
storage, no host name.

| File | Its part |
|---|---|
| `benchmarks/adapter_eval/race/lane.py` | one lane: slots, recording, metrics |
| `benchmarks/adapter_eval/race/run_race.py` | the pod's run: workload, adapters, SR checkpoint, both lanes |
| `benchmarks/adapter_eval/race/react.py` | the ReAct agents, from the switch benchmark's generator |
| `benchmarks/gen_agent_configs.py` | that generator, copied unchanged |
| `benchmarks/adapter_eval/race/build_page.py` | a race into the page on main |
| `tests/unit/test_agent_race.py` | the race end to end on CPU, with a fake engine |
